1Person supports **13 AI coding tools**. They all implement the same interface — queue, dispatch, execute, return results — so you can drive any of them from the same 1Person board. **But the capability details diverge significantly**: whether session resumption actually works, whether MCP is supported, where skill files live, how models are selected. This page is the full matrix.

<Callout type="warning">
The local daemon drives **five** of these today: **OpenCode, Claude Code, Codex, DeepSeek Harness and Pi**. It has no code path for the other eight — it does not detect them, and a runtime registered for one of them cannot execute a task. Every row below says which is which, and the capability columns say what the daemon actually does, not what the CLI could do in principle.
</Callout>

For guidance on picking a tool when creating an agent, see [Creating and configuring agents](/agents-create).

## What each tool is for

### Antigravity

From Google. CLI binary name is `agy`. Pairs with Google's Antigravity service and ships with a Gemini-backed default model. The CLI can resume a conversation (`--conversation <id>`) and can list its model catalog (`agy models`). **The local daemon has no code path for agy** — it neither detects nor runs it, so none of that is reachable from 1Person today.

### Claude Code

From Anthropic. The CLI supports session resumption, reads MCP configuration, and takes fine-tuning flags like `--max-turns` and `--append-system-prompt`; it needs an Anthropic API key. **The local daemon drives it**, in the plain non-interactive form: one prompt in, the answer out. The daemon hands it no session id and passes no MCP configuration through.

### Codex

From OpenAI. Uses JSON-RPC 2.0, has stronger statefulness, and a finer-grained approve mechanism (manual approval for `exec_command` and `patch_apply`). **The local daemon drives it** through `codex exec` with a read-only sandbox, so a task that only answers never touches the disk. The CLI's own default model is used.

### Copilot

From GitHub. Model routing goes through your GitHub account entitlement — the tool doesn't select a model itself; GitHub decides which model you get. **The local daemon has no code path for it** today.

### Cursor

From Anysphere, the CLI counterpart to the Cursor editor. The CLI can be driven headlessly and reads MCP configuration from `.cursor/mcp.json`. **The local daemon has no code path for it** today.

### Gemini

From Google, supports the Gemini 2.5 and 3 series. **The local daemon has no code path for it** today.

### Hermes

From Nous Research. Uses the ACP protocol (shares a transport with Kimi). **The local daemon has no code path for it** today.

### Kimi

From Moonshot, aimed at the Chinese market. Shares the ACP protocol with Hermes. **The local daemon has no code path for it** today.

### Kiro CLI

From Amazon. Uses ACP over stdio via `kiro-cli acp`. **The local daemon has no code path for it** today.

### OpenCode

From SST, open source. Dynamically discovers available models and model variants from its own configuration file — a good fit for users who want to bring their own model catalog. **The local daemon drives it**, and it is the default choice: it answers without a paid subscription. The daemon writes its own agent profile into the task's working directory (a task that only answers gets no tools at all), passes the agent's model as `--model`, and runs the CLI against a private server so the profile next to the task is the one that applies. It resumes no session and passes no MCP configuration through.

### OpenClaw

Open-source project, a CLI agent orchestrator. Configuration is strictly controlled: users can't pass `--model` or `--system-prompt`; the agent-registration config decides. **The local daemon has no code path for it** today.

### DeepSeek Harness

From DeepSeek, built on the DeepSeek Harness. **The local daemon drives it** through its headless profile: one task in, the answer on stdout, the process exits. Every task starts fresh — the CLI can resume a session with `--session-id`, but the daemon does not use that — and the profile's own default model is used. The CLI installs itself under its own home directory (`~/.dsh`) rather than on `PATH`, so the daemon looks there for it.

### Pi

From Inflection AI, minimalist. **The local daemon drives it** through its non-interactive mode (`pi -p`): the prompt is processed, the answer comes back on stdout, the process exits. The daemon writes no session file, so every task starts fresh. The CLI installs its launcher under `~/.pi/agent` rather than on `PATH`; the daemon looks there too.

## Session resumption: not wired up yet

The session resumption mechanism is covered in [Tasks](/tasks#can-a-task-continue-from-the-previous-context). Here's the **exact current state**:

| Status | Tools | Meaning |
|---|---|---|
| ❌ Not implemented | All 13 | The daemon never hands a session id to the CLI, so every task starts from a clean context |

**For your decision**: a workflow that needs the agent to keep context across tasks (failure retries, manual reruns, conversational iteration) does not get that from the CLI today, on any tool. [Chat](/chat) keeps its context a different way — the server renders the conversation into the prompt, so the agent reads the history instead of resuming a session.

## MCP configuration: accepted, not passed through

**No tool consumes `mcp_config` in the local daemon.** The field is stored on the agent and travels to the daemon with the task, but the daemon does not hand it to any CLI — so the servers you configure have no effect, on every tool, with no error and no warning.

Each tool would need its own path for this to work (Claude Code takes `--mcp-config` with `--strict-mcp-config`, Codex wants a `mcp_servers` block in `$CODEX_HOME/config.toml`, the ACP family takes `mcpServers`), and none of those paths are wired up yet.

<Callout type="warning">
If you configure `mcp_config` on an agent today, your MCP servers **do not reach the agent**. Nothing warns you about it — the configuration is simply dropped on the way to the CLI.
</Callout>

## Where skill files go

Each tool uses **its own** skill discovery path. The table below is where each CLI reads skills from — the paths the tools themselves document:

| Tool | Path | Native discovery? |
|---|---|---|
| Claude Code | `.claude/skills/` | ✅ Native |
| Codex | `$CODEX_HOME/skills/` | ✅ Native |
| Copilot | `.github/skills/` | ✅ Native |
| Cursor | `.cursor/skills/` | ✅ Native |
| Kimi | `.kimi/skills/` | ✅ Native |
| Kiro CLI | `.kiro/skills/` | ✅ Native |
| OpenCode | `.opencode/skills/` | ✅ Native |
| Pi | `.pi/skills/` | ✅ Native |
| Antigravity | `.agents/skills/` | ✅ Native (inherits Gemini CLI's workspace layout — see [Antigravity docs](https://antigravity.google/docs/gcli-migration)) |
| Gemini | `.agent_context/skills/` | ⚠️ Generic fallback |
| Hermes | `.agent_context/skills/` | ⚠️ Generic fallback |
| OpenClaw | `.agent_context/skills/` | ⚠️ Generic fallback |

**The daemon does not copy skill files into the task workspace yet.** It scans the local skills directory and reports a placeholder list back to the server, so a skill that looks attached in the UI is not necessarily handed to the CLI.

For creating and using skills, see [Skills](/skills).
