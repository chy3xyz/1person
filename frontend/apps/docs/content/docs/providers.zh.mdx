1Person 支持 **13 款 AI 编程工具**。它们实现的是同一套接口——排队、派发、执行、结果回传——所以你可以从 1Person 的同一个看板上指挥任意一款。**但它们在能力细节上差异很大**：会话恢复是不是真用、MCP 支不支持、skill 文件该放哪儿、模型怎么选。这一页是完整对照。

<Callout type="warning">
本地守护进程目前只能驱动其中 **5 款**：**OpenCode、Claude Code、Codex、DeepSeek Harness 和 Pi**。另外 8 款它没有代码路径——既不检测，也不运行；为它们注册的运行时跑不了任务。下面每一行都标明谁属于哪一类，能力列写的是守护进程实际会做的事，不是 CLI 理论上能做的事。
</Callout>

创建智能体时挑选工具的指引见 [创建和配置智能体](/agents-create)。

## 每款工具的定位

### Antigravity

Google 出品。CLI 二进制名是 `agy`，搭配 Google Antigravity 服务，默认走 Gemini 系的模型。CLI 本身能恢复一段对话（`--conversation <id>`），也能列出模型目录（`agy models`）。**本地守护进程没有 agy 的代码路径**——既不检测也不运行，所以这些能力今天从 1Person 够不着。

### Claude Code

Anthropic 出品。CLI 支持会话恢复、会读 MCP 配置，还接受 `--max-turns`、`--append-system-prompt` 这类细调参数；需要 Anthropic API 密钥。**本地守护进程能驱动它**，走的是最朴素的非交互形式：进一个提示词，出一个答案。守护进程不会给它 session id，也不会把 MCP 配置传下去。

### Codex

OpenAI 出品。使用 JSON-RPC 2.0，状态化更强，approve 机制也更细（`exec_command` 和 `patch_apply` 手动批准）。**本地守护进程能驱动它**，走 `codex exec` 并开只读沙盒，所以只做问答的任务不会碰磁盘。用的是 CLI 自己的默认模型。

### Copilot

GitHub 出品。模型路由走你的 GitHub 账号权益——工具自己不选模型，由 GitHub 决定你拿到哪个模型。**本地守护进程今天没有它的代码路径**。

### Cursor

Anysphere 出品，Cursor 编辑器的 CLI 对应物。CLI 可以无头驱动，也会从 `.cursor/mcp.json` 读 MCP 配置。**本地守护进程今天没有它的代码路径**。

### Gemini

Google 出品，支持 Gemini 2.5 和 3 系列。**本地守护进程今天没有它的代码路径**。

### Hermes

Nous Research 出品。使用 ACP 协议（和 Kimi 共享传输层）。**本地守护进程今天没有它的代码路径**。

### Kimi

Moonshot 出品，面向中国市场。和 Hermes 共享 ACP 协议。**本地守护进程今天没有它的代码路径**。

### Kiro CLI

Amazon 出品。通过 `kiro-cli acp` 使用 ACP over stdio。**本地守护进程今天没有它的代码路径**。

### OpenCode

SST 出品，开源。从自己的配置文件里动态发现可用模型和模型 variant——适合想自带模型清单的用户。**本地守护进程能驱动它**，而且它是默认选择：不用付费订阅也能出答案。守护进程会把自己的 agent profile 写进任务的工作目录（只做问答的任务一个工具都拿不到），把智能体的模型以 `--model` 传进去，并让 CLI 跑在一个私有 server 上，这样紧挨任务的 profile 才是生效的那份。它不恢复任何会话，也不把 MCP 配置传下去。

### OpenClaw

开源项目，一个 CLI agent 编排器。配置严格受控：用户不能传 `--model` 或 `--system-prompt`，由智能体注册时的配置决定。**本地守护进程今天没有它的代码路径**。

### DeepSeek Harness

DeepSeek 出品，基于 DeepSeek Harness。**本地守护进程能驱动它**，走它的 headless profile：进一个任务，答案打到 stdout，进程退出。每个任务都从零开始——CLI 本身可以用 `--session-id` 续跑会话，但守护进程没用上——用的是 profile 自带的默认模型。这个 CLI 装在自己的家目录（`~/.dsh`）下而不是 `PATH` 上，所以守护进程是去那里找它的。

### Pi

Inflection AI 出品，极简。**本地守护进程能驱动它**，走它的非交互模式（`pi -p`）：提示词被处理，答案回到 stdout，进程退出。守护进程不写 session 文件，所以每个任务都从零开始。这个 CLI 把启动器装在 `~/.pi/agent` 下而不是 `PATH` 上；守护进程也会去那里找。

## 会话恢复：还没接上

会话恢复的机制在 [执行任务](/tasks#任务能接着上次的上下文继续吗) 里讲过。这里是**精确现状**：

| 状态 | 工具 | 含义 |
|---|---|---|
| ❌ 未实现 | 全部 13 款 | 守护进程从不把 session id 交给 CLI，所以每个任务都从干净的上下文开始 |

**对你的决策**：需要智能体在多次任务之间保持上下文的工作流（失败重试、手动重跑、对话式迭代），今天在任何一款工具上都不会从 CLI 拿到这个能力。[对话](/chat) 用的是另一套办法——服务端把对话历史渲染进提示词，智能体是在读历史，而不是在续跑会话。

## MCP 配置：收了，但没往下传

**本地守护进程里，没有任何一款工具消费 `mcp_config`。** 这个字段存在智能体上，会随任务一起传到守护进程，但守护进程不会把它交给任何 CLI——所以你配的 MCP server 在所有工具上都不生效，没有报错，也没有警告。

要让它生效，每款工具都需要自己的接入路径（Claude Code 走 `--mcp-config` 配 `--strict-mcp-config`，Codex 要在 `$CODEX_HOME/config.toml` 里写 `mcp_servers` block，ACP 系列走 `mcpServers`），而这些路径一条都没接上。

<Callout type="warning">
今天在智能体上配了 `mcp_config`，你的 MCP server **到不了智能体**。没有任何提示——配置就在传给 CLI 的路上被丢掉了。
</Callout>

## skill 文件该放哪儿

每款工具用**自己**的 skill 发现路径。下面这张表是各 CLI 读 skill 的位置——都是工具自己文档里写的路径：

| 工具 | 路径 | 是否原生发现 |
|---|---|---|
| Claude Code | `.claude/skills/` | ✅ 原生 |
| Codex | `$CODEX_HOME/skills/` | ✅ 原生 |
| Copilot | `.github/skills/` | ✅ 原生 |
| Cursor | `.cursor/skills/` | ✅ 原生 |
| Kimi | `.kimi/skills/` | ✅ 原生 |
| Kiro CLI | `.kiro/skills/` | ✅ 原生 |
| OpenCode | `.opencode/skills/` | ✅ 原生 |
| Pi | `.pi/skills/` | ✅ 原生 |
| Antigravity | `.agents/skills/` | ✅ 原生（沿用 Gemini CLI 的 workspace 布局——见 [Antigravity 文档](https://antigravity.google/docs/gcli-migration)）|
| Gemini | `.agent_context/skills/` | ⚠️ 通用 fallback |
| Hermes | `.agent_context/skills/` | ⚠️ 通用 fallback |
| OpenClaw | `.agent_context/skills/` | ⚠️ 通用 fallback |

**守护进程目前不会把 skill 文件复制进任务工作区。** 它只扫描本机的 skill 目录，然后回一份占位列表给服务器——所以在界面上看着像是挂上了的 skill，不一定会真的交到 CLI 手里。

skill 的创建和使用详见 [技能](/skills)。
