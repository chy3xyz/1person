在 1Person 里，一个**运行时**（runtime）就是你机器上的守护进程，配上守护进程找到的某一款 AI 编程工具。如果上手引导的"连接运行时"这一步显示 **未检测到支持的工具**，说明守护进程扫过了你的机器，但它会驱动的 5 款工具一个都没找到。装下面任意一款工具，回到这一步重新扫描，几秒内运行时就会出现。

这一页是装机的入口，和它配套的是：

- [守护进程与运行时](/daemon-runtimes) —— 检测是怎么工作的
- [AI 编程工具矩阵](/providers) —— 每款工具的能力差异（会话恢复、MCP、模型选择）

<Callout type="info">
1Person 服务器从不接触你的 API key，也不接触工具本身。下面这些操作——安装、登录、模型访问——全部发生在你本机。出问题几乎都是本地问题。
</Callout>

## 开始前

下面每一款工具都有两个共同前提：

1. **1Person 守护进程在运行。** 装完 [1Person CLI](/cli) 后跑 `1person daemon start`；或者用 [1Person 桌面端](/desktop-app)，它启动时自动拉起守护进程。守护进程没起来，就没人去扫工具。
2. **工具得能被找到。** 守护进程通过名字 shell out 调起工具（见每一节里**守护进程扫描**那行的命令名），`PATH` 是常规位置。其中两款——DeepSeek Harness 和 Pi——装在自己的家目录下，守护进程也会去那里找，所以不需要做软链接。终端里 `which <名字>` 找不到，守护进程也找不到。装完后打开新终端（或者重启守护进程），让新的 `PATH` 生效。

装完一款工具后，重启守护进程：

```bash
1person daemon restart
```

桌面端的话，重启 app 即可。守护进程每次启动都会重新扫描。

## 守护进程能驱动的 5 款工具

大致按常见程度排序。挑你已经有凭证的那一款就行——不需要全都装。

### OpenCode（SST）

开源 CLI agent，也是守护进程的默认选择：不用付费订阅也能出答案。从自己的配置文件里动态发现可用模型——适合想自带模型清单的用户。守护进程会把智能体的模型以 `--model` 传进去；它不恢复任何会话，也不把 MCP 配置传下去。

| | |
|---|---|
| 守护进程扫描 | `opencode` |
| 安装 | 看官方指引 [opencode.ai](https://opencode.ai/) 或仓库 [github.com/sst/opencode](https://github.com/sst/opencode)。一般是装脚本或 npm 包。 |
| 认证 | 按 OpenCode 的文档配你自己的模型供应商（Anthropic、OpenAI 等）。 |

### Claude Code（Anthropic）

走的是最朴素的非交互形式：进一个提示词，出一个答案。CLI 本身支持会话恢复、MCP 配置和 `--max-turns` 这类细调参数，但守护进程今天一个都没给它。

| | |
|---|---|
| 守护进程扫描 | `claude` |
| 安装 | 看官方指引 [claude.com/claude-code](https://www.claude.com/claude-code)。常见装法是 npm 包 `@anthropic-ai/claude-code`（需要 Node.js 18+）。 |
| 认证 | 跑一次 `claude`，跟着 CLI 里的登录流程走；或者设置 `ANTHROPIC_API_KEY`。 |

### Codex（OpenAI）

JSON-RPC 2.0 传输，审批粒度更细。守护进程用 `codex exec` 跑它并开只读沙盒，所以只做问答的任务不会碰磁盘。用的是 CLI 自己的默认模型。

| | |
|---|---|
| 守护进程扫描 | `codex` |
| 安装 | 看官方指引 [github.com/openai/codex](https://github.com/openai/codex)。常见装法是 npm 包 `@openai/codex`。 |
| 认证 | `codex login`（浏览器登录），或 `OPENAI_API_KEY`。 |

### DeepSeek Harness（DeepSeek）

一个基于插件搭起来的 agent harness。守护进程驱动它的 **headless profile**：进一个任务，答案打到 stdout，进程退出。这个 CLI 装在 `$DSH_HOME`（默认 `~/.dsh`）下而不是 `PATH` 上，守护进程也会去那里找。

| | |
|---|---|
| 守护进程扫描 | `dsh`——在 `PATH` 上，或者 `$DSH_HOME/profiles/node_modules/@deepseek-ai/dsh/lib/bin.js` |
| 安装 | 看 DeepSeek Harness 的仓库 [github.com/deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)。 |
| 认证 | 需要 DeepSeek API 密钥（`DEEPSEEK_API_KEY`），通过 harness 自己的凭证服务配置。 |

### Pi（Inflection AI）

极简。守护进程通过它的非交互模式（`pi -p`）驱动：提示词被处理，答案回到 stdout，进程退出。这个 CLI 把启动器装在 `$PI_CODING_AGENT_DIR`（默认 `~/.pi/agent`）下而不是 `PATH` 上，守护进程也会去那里找。

| | |
|---|---|
| 守护进程扫描 | `pi`——在 `PATH` 上，或者 `$PI_CODING_AGENT_DIR/bin/pi` |
| 安装 | 看 Inflection 的 CLI 文档 [pi.ai](https://pi.ai/)。 |
| 认证 | 按厂商文档。 |

## 在名单上、还驱不动的工具

这 8 款属于 1Person 的工具名单，但守护进程对它们没有代码路径：既不检测，也不运行，所以在那之前装它们不会带来任何变化。安装和认证说明留在这里，是为了让支持真正落地时，这一页仍然是唯一要查的地方。

### Cursor（Anysphere）

Cursor 编辑器的 CLI 对应物。

| | |
|---|---|
| 守护进程扫描 | `cursor-agent`——暂不支持 |
| 安装 | 先装 [Cursor 编辑器](https://cursor.com/)，再按 [docs.cursor.com](https://docs.cursor.com/) 的说明装 CLI。可执行文件叫 `cursor-agent`，不是 `cursor`。 |
| 认证 | 在 Cursor 编辑器里登录，CLI 复用同一份会话。 |

### GitHub Copilot

模型走的是你 GitHub 账号的 entitlement——工具自己不挑模型，GitHub 决定你拿到哪个模型。

| | |
|---|---|
| 守护进程扫描 | `copilot`——暂不支持 |
| 安装 | 看 GitHub 的 CLI 文档 [github.com/github/copilot-cli](https://github.com/github/copilot-cli)。 |
| 认证 | CLI 里走 GitHub 浏览器登录。 |
| 备注 | 登录账号必须有有效的 GitHub Copilot 订阅。 |

### Gemini（Google）

支持 Gemini 2.5 和 3 系列。

| | |
|---|---|
| 守护进程扫描 | `gemini`——暂不支持 |
| 安装 | 看官方指引 [github.com/google-gemini/gemini-cli](https://github.com/google-gemini/gemini-cli)。常见装法是 npm 包 `@google/gemini-cli`。 |
| 认证 | 跑 `gemini` 会提示 Google 账号登录，或设置 `GEMINI_API_KEY`。 |

### Kiro CLI（Amazon）

ACP-over-stdio 传输。

| | |
|---|---|
| 守护进程扫描 | `kiro-cli`——暂不支持 |
| 安装 | 看 Kiro 的文档 [kiro.dev](https://kiro.dev/)。可执行文件叫 `kiro-cli`，不是 `kiro`。 |
| 认证 | 基于 AWS 账号，按 Kiro 自己的引导走。 |

### Kimi（Moonshot）

ACP 协议 agent，主要面向中国市场。

| | |
|---|---|
| 守护进程扫描 | `kimi`——暂不支持 |
| 安装 | 看官方指引 [github.com/MoonshotAI/kimi-cli](https://github.com/MoonshotAI/kimi-cli)。 |
| 认证 | Moonshot API key，按厂商文档配置。 |

### Hermes（Nous Research）

ACP 协议 agent（和 Kimi 共享传输层）。

| | |
|---|---|
| 守护进程扫描 | `hermes`——暂不支持 |
| 安装 | 看 Nous Research 的仓库 [github.com/NousResearch](https://github.com/NousResearch) 获取最新 CLI。 |
| 认证 | 按厂商文档。 |

### OpenClaw

开源 CLI agent 编排器。**模型绑在智能体层**（`openclaw agents add --model`）——不能按任务覆盖。

| | |
|---|---|
| 守护进程扫描 | `openclaw`——暂不支持 |
| 安装 | 看项目 [github.com/openclaw-org/openclaw](https://github.com/openclaw-org/openclaw)（社区维护）。 |
| 认证 | 按 OpenClaw 的文档配底层模型供应商。 |

### Antigravity（Google）

Google 的 Antigravity CLI（`agy`）。搭配 Google Antigravity 服务，跑 Gemini 系的模型。

| | |
|---|---|
| 守护进程扫描 | `agy`——暂不支持 |
| 安装 | 看官方指引 [antigravity.google/docs/cli-overview](https://antigravity.google/docs/cli-overview)。CLI 是预编译的，跑一次 `agy install` 配好 PATH 和 shell 别名即可。 |
| 认证 | 交互式跑一次 `agy` 走 Google 账号登录流程；或者通过 Antigravity 桌面端登录——CLI 会复用 GUI 写入 keyring 的凭据。 |

## 装完之后

1. **确认可执行文件能被找到。** 开一个新终端，跑 `which <名字>`（比如 `which claude`、`which opencode`、`which dsh`、`which pi`）。打印出路径，守护进程就找得到——`dsh` 和 `pi` 就算没有 `PATH` 条目也能被找到。什么都不打印，先修 shell 的 `PATH`（最常见原因是 rc 文件没重新加载）。
2. **重启守护进程。** `1person daemon restart`，或者重启桌面端。守护进程只在启动时扫描。
3. **看 Runtimes 页面。** 1Person UI 的 **Runtimes** 页应该会出现守护进程挑中的那款工具对应的运行时。如果显示 "offline"，看[守护进程与运行时 → 运行时什么时候被判定为离线](/daemon-runtimes#运行时什么时候被判定为离线)。
4. **回到上手引导。** "连接运行时" 这一步会一直轮询，几秒内就能扫到新运行时，不需要手动刷新。

## 排错

- **`which` 找得到，但守护进程找不到。** 守护进程是用旧 `PATH` 启的，重启它。
- **挑错了工具。** 守护进程按固定顺序取第一个能跑的。用 `ONEPERSON_AGENT_PROVIDER` 点名指定你想要的那款，然后重启守护进程。
- **可执行文件在，但启动就失败。** 在终端单独跑一次工具的 `--version` 或 `--help`，绝大多数失败都是登录没做、token 过期、Node.js / 运行时版本不对。
- **Runtimes 页面看到行，但任务一跑就失败。** 一边触发任务一边跑 `1person daemon logs -f`。守护进程会把工具自己的报错原样吐出来。

更宽的症状看[排错指南](/troubleshooting)。
